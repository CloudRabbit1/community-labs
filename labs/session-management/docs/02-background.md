# Background

## What Makes a Good Session Token

A session token needs three properties:

1. Long enough to prevent brute force (at least 128 bits of entropy).
2. Unpredictable: generated by a cryptographically secure random number generator (CSPRNG).
3. Not reused: each login issues a fresh token.

The Python standard library covers this: `secrets.token_hex(32)` generates a 64-character hex string from OS entropy. Web frameworks do the same automatically when you use their session middleware.

## Sequential Tokens

A counter-based token fails all three tests. The namespace is tiny (session_1, session_2, ...), the next value is trivially predictable, and every token ever issued is still valid until logout.

## Relationship to IDOR

Session prediction is a special case of IDOR: the resource identifier (session token) is both predictable and directly tied to a privileged record. The difference is that session tokens are supposed to be opaque credentials, not database IDs.
